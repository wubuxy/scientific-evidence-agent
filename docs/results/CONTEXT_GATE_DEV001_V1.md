## 这次定位到的执行问题

两次都按相同顺序行动：规划 → 对第一篇执行四个搜索 → 对第二篇执行四个搜索 → 被预算控制器强制收尾 → 连续三次报告校验失败。

程序虽然在提示中要求“搜索后回读”，却没有在动作层控制这个转换。搜索结果占用了输入空间，收尾又只提供实际回读的证据；因为实际回读为空，写作阶段没有可引用原文。两次共 **24,421 token** 花在这些无证据的收尾调用上。这是已测消耗，不是修复后已实现的节省。

上一轮缩短收尾提示、分离方案格式和修正预算预留仍不够；新提示取消了固定摘要阅读，模型却先铺开搜索。多项变化同时存在，不能把退化单独归因于某一行提示，也不能据此判断数据或模型容量是根因。当前可以直接处理的缺口，是已有命中后迟迟不读，以及无证据时仍反复写报告。

## 在两次尝试结束后修复

新增 `grounding.py` 和 Runtime 的回读阶段：

1. 已有计划，且一批搜索返回尚未被实际回读覆盖的窗口时，下轮进入回读阶段。
2. 按论文与查询交替提供有限的定位预览；保留问题和完整字段标准，只开放 `sources_read`。模型选择具体窗口，也可一次读取多个窗口。程序实际拒绝在此阶段继续搜索或写报告。
3. 成功回读后恢复研究工具。错误回读的反馈在重建上下文时保留，供下一次修正参数。只是取得可引用原文，不自动宣告字段正确或证据充分；空搜索结果不会强制读取不存在的命中，已完整回读的窗口也不触发重复读取。
4. 有搜索线索、没有任何已读证据，而剩余步数、时间或预估预算已不允许继续时，记录 `no_read_evidence` 并失败，停止付费写作重试。已有部分真实证据时仍可交付明确不完整的报告。

运行事件包括 `read_checkpoint_requested`、`read_checkpoint_blocked`，预算记录增加 phase；界面说明当前是在回读还是因缺少已读证据停止。设计沿用[上下文工程与充分性分析的阅读依据](CONTEXT_REPAIR_V1.md#阅读依据与采用边界)，这是本项目的执行控制设计，不是某篇论文方法的复现。
