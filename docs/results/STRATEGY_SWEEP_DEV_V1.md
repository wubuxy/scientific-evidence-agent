**原文片段选择值得优先继续验证；把所有策略叠起来没有胜出。** 本轮验证了工程交付差异，尚未产生人工语义准确率。默认记忆模式与策略开关未因这次小样本切换。

分任务看，原文片段选择在两类问题上均为 2/2；组合版在评测设计题上 2/2，在角色／训练／评测条件辨析题上 0/2。精简协议在后者为 2/2，但其中一份明确保留两个未核实字段。更少重复阅读没有自动带来更高交付率。

原文片段选择比基线平均多用约 **2.80%** token；精简协议平均少用约 **2.92%**。这些是本轮描述性数字。每组四次并非四个独立任务；两个问题还共享论文，且各条件独立生成轨迹，因此不计算显著性，也不报告“准确率提升”。

## 失败具体发生在哪里

1. **七次存在无引用声明。** 输出中的 `claims[*].evidence_ids` 为空，报告被拒绝，剩余预算不足以重新提交。一些未核实判断应放在限制或有条件方案中，不能通过放松引用要求解决。
2. **一次 JSON 未完成。** `design-read-first-02` 的输出停在 `proposals`，用了全部 1,800 个输出 token。供应商仍报告 `finish_reason=tool_calls`，因此只统计 `finish_reason=length` 会漏掉它；原始输出与解析错误都保留。
3. **一次实际用量超限。** `conditions-combined-01` 返回 30,855 token，比目标多 855。提示 token 是启发式估计，跨阶段校准低估了最终请求；本次按失败处理，完整计费，不能称为严格未超限。
4. **交付也可能不完整。** 阅读导航的一份报告未逐字使用指定字段名，八项仍为 missing；精简协议的一份报告保留两项未知。两者都没有被算成字段完整。

上述失败说明当前瓶颈不仅在检索：报告一次性生成、无引用的判断如何表达，以及输出空间分配，都需要单独处理。没有把程序拒绝的草稿静默改写成“成功报告”。

## 本轮顺手修复的真实缺陷

冻结实验全部结束后，合入独立工作区验证的预算修复（`af594cc`）：

- 超限返回带着实际用量穿过评测边界，主循环与核验阶段都先记账再终止；不会漏掉最后一笔费用。
- 超预算异常不能进入可恢复工具错误路径，也不能回退成旧报告的“成功”；用量耗尽后禁止进一步调用。
- 校准系数保留已观察到的较高值，且不低于初始值，避免较便宜阶段把后续预留调低。这仍是保守估计，不是供应商精确分词计费保证。

以上修复经过离线回归，**没有把修复后的行为冒充为这 24 次实验的版本，也没有追加真实调用来宣称修复后的交付效果**。

冻结记录中的异常保持原样：超限那次运行计数为 21,345，而评测轨迹计数为 30,855。审计仅在“明确预算异常、最后一次返回未入账、先前事件逐笔一致”这一精确模式下解释差额 9,510；输出单独列出两个计数及超限值，不修改或忽略原始费用。

## 接下来保留什么

- **优先评审原文片段选择**，检查关键限定条件是否保留，避免把交付率当成支持度。
- **精简协议作为次选**，先看它省略通用列后是否损失必要条件，再考虑默认化。
- **阅读导航、已读优先和组合保留为实验开关**，本轮未显示稳定交付优势。减少重复读仍是有用诊断，但不是独立成功目标。
- 下一轮先处理报告中“事实／推断／未核实限制／方案”的边界和局部修正，继续沿用固定要求、严格引用和失败计数；不因本轮数据直接上训练或多 Agent。
