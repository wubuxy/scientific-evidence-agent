# 核验器对照的模型释放修复记录

日期：2026-11-06。在首个正式运行 `run-001` 中，第一个 BF16 LoRA 种子完成 128 步，耗时约 214 秒；第二个种子的最后一条进度日志仅到第 8 步，已耗时约 575 秒。进程显存接近整卡容量，运行被主动中断，原始预测、训练日志及 `operator-interruption.json` 保留。此时没有读取新测试集标签或据此选择方法。

原因是清理代码使用 `if "base" in locals(): del base`。在服务器 Python 3.12 中，`locals()` 会同步并保留函数帧的字典；删除快速局部变量后，字典仍可能持有上一基础模型的强引用。弱引用最小复现确认了这一保留行为。加载下一 BF16 模型时，两个基础模型同时存活，显著变慢的行为与共享显存分页一致；没有把驱动报告的物理显存使用量当作 PyTorch 分配总量。

修复在每个条件开始时显式初始化 `model` 和 `base`，在清理阶段将两者设为 `None`，再执行垃圾回收与 CUDA 缓存释放，不再通过 `locals()` 检查模型句柄。新增的生命周期回归使用弱引用、伪模型及完整条件循环，覆盖基础模型加载、适配器训练、重新加载和跨种子切换；每次新加载都要求上一基础模型已释放。

原运行和原冻结清单不覆盖。修复后生成新的 plan 和硬件预检，重新提交冻结记录，再完整执行全部条件。模型、原文、测试 ID、提示、标签、随机种子、训练步数、优化器及评分协议沿用原计划，不依据测试效果调整。第一次中断运行的缺失种子仍计入该版本的分母；修复后的完整运行单独报告，不能把两次运行中较好的条件拼成一组。

中断版本的评分留到修复后的完整生成结束后，使用原提交的独立工作树执行。这样既保留失败分母，也避免在修复资源问题时利用正式测试标签。修复是否解决跨种子资源保留，以服务器 Python 3.12 回归、后续种子耗时与显存记录共同验证。
