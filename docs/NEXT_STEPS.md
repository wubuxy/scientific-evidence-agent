# 下一步：证明研究价值，补齐执行与评测闭环

2026-11-08。根据 Agent 开发实习岗位要求与当前仓库核查更新。以下是工作顺序与验收建议，不是实验预注册；新任务、评分表、预算和模型配置仍须在运行前冻结。

## 当前定位与岗位要求

定位为“面向科研文献调研的证据约束 Agent，包含执行控制与自动化评测工具链”。论文场景足以展示工具调用、任务编排、检索、上下文和评测能力；开放式研究判断还需要真实任务验证。

| 岗位关心什么 | 已有可检查证据 | 还需要补什么 |
|---|---|---|
| 编程、调试与搭建 Agent | Python Runtime、工具 schema、FastAPI、工作区隔离、CI | 候选人现场追踪执行、定位问题和修改代码，仓库不能代替本人能力验证 |
| 工具调用、任务编排、RAG、上下文管理 | 多轮工具选择、Grep / hybrid 检索、原文回读、写作上下文预算 | 用一条完整任务讲清动作选择、信息缺口、停止与失败 |
| 拆解开放问题、实验验证 | 冻结协议、配对对照、失败分母、成本与负结果 | 研究判断任务和按任务目标制定的评分表 |
| 关注效果与用户反馈 | 16 份真实报告、92 条待盲审单元 | 两人独立标签、真实使用反馈及据此修复问题的记录 |
| Agent harness / 自动评测加分项 | 执行预算、状态与回退、生产 Runtime 评测、故障回归 | 故障矩阵汇总、运行前要求确认、运行审计包 |
| 后端与开源工程加分项 | 公开仓库、Docker、本机演示、跨平台 CI | 按实际使用需求补运维能力；当前未证明生产并发与服务规模 |
| 检索 / 训练 / 实验分析加分项 | BM25 / dense RRF、A5000 LoRA 与外部核验器对照 | 模块实验与端到端收益分开表述，未达采用门槛的模型保持候选状态 |

该岗位未要求多 Agent、自动进化或新训练。是否新增这些机制，应由真实失败和公平对照决定。现有单 Agent 的执行控制可以作为 harness 实践讲解，不包装成已完成的通用框架。

## P1：完成一个有研究判断的端到端任务

先选一个真正需要作出选择的问题。例如：“在给定数据与计算预算下，比较几类交通流预测方案；判断论文实验是否可比，列出支持与反对证据，提出最小验证计划。”这是候选任务示例，尚未生成报告或验证能力；具体领域应选用户能核验且有资料的场景。

交付标准应覆盖：候选方案与来源、比较条件、关键反例、信息缺口、结论及适用条件、下一步验证。找到字段不等于完成分析；无法支持结论时允许保留未知。

先做固定资料包下的分析，分离“找到资料”与“利用资料”的效果；之后再单独评估联网发现，保存搜索结果快照及全文获取失败。固定资料也可以包含深度分析，无须一开始同时解决所有信息源。

建议准备 6–10 个开发任务，每条件重复两次，先比较同一模型、相同语料和总 token 上限的三个条件：

| 条件 | 目的 | 公平性约束 |
|---|---|---|
| 一次性报告 | 检查多轮行动是否有必要 | 使用可容纳完整资料包的任务；输入包含同样的来源与行地址。若必须截断，单独标记，不能当作全文强基线 |
| 原有多轮 Agent，关闭字段控制 | 检查工具循环的表现 | 固定模型、可用工具和预算，保持输出契约一致 |
| 多轮 Agent，启用字段控制 | 检查状态与有界补救是否有净价值 | 核验与补读计入同一总上限，报告实际 token 与耗时 |

这是 36–60 个计划结果的小规模开发 pilot，不宣称统计显著或外部最强基线。若要把提升归因到“定向修复”，仍需加入同预算普通补搜条件；三组总体验证不能替代机制消融。

评分表先于输出固定，包含关键证据覆盖、比较条件正确性、结论支持、反例与不确定性、建议可执行性。至少两人独立盲评后仲裁，同时保留逐题变化、成本、缺失和失败。模型评分只作辅助；按共享论文分组分析，不能把重复运行当独立问题。已有 QASPER 200 题保留集保持隔离。

先做一个开发案例确认任务与评分能用，再冻结 pilot；一份展示报告只能说明流程，不能证明普遍效果。即使收益为零，也应交付失败分类与下一次可验证的改进假设。

**本轮进展**：已用现有两篇演示论文执行“为文献 Agent 设计评测组合”的单个开发案例，并在修复程序错误后复跑。两次均因无引用分析与后续预算不足失败；输入、rubric、两次轨迹和失败草稿均已归档。下一步先明确事实、分析与待验证建议的输出契约，以及评测章节的阅读需求，再冻结质量 pilot。见[案例诊断](results/RESEARCH_JUDGMENT_DEV001.md)。

## P2：将已有执行控制整理成可复查的工程能力

前两项已经落地并验证，第三项仍待实现；无需另写一套 Agent 框架。

| 顺序 | 工作 | 验收 |
|---|---|---|
| 已完成 | 用户运行前确认论文与字段要求 | 编辑器发送显式要求；生产 API 回归检查标准进入模型上下文并持久化；前端检查非法提交及跨课题清空 |
| 已完成 | 将已有故障回归整理为独立汇总命令 | `scripts/eval_agent_faults.py` 汇总 17 个场景；保留预期行为和实际结果，缺失与跳过不能算通过，CI 上传结果 |
| 3 | 运行级审计包导出 | 串起 run、工具事件、原文、候选版本、核验、失败和已知成本；校验所有权，脱敏并限制大小；不包含密钥 |

现有检查点用于保留报告与失败回退，不等于已实现任意中断后的精确恢复。故障评测应依据实际支持范围验收，不为求完整而宣称不存在的恢复机制。

## P3：完成语义校准与真实使用反馈

- 完成已准备的 92 条自然声明双人盲审。独立提交前不展示模型意见，仲裁后报告一致性、引用支持指标和核验器误判。
- 这批标签只校准声明支持，不能替代研究充分性、字段完成度或 P1 的研究判断评分。
- 邀请 2–3 位有实际文献调研需求的使用者完成任务，记录是否解决问题、到可用答案的时间、引用核查负担和主要失败；有条件时与其原有工作方式对照。属于形成性反馈，不夸大成用户效果结论。
- 按反馈选择一个错误类型修复，再在未参与修改的新任务上验证。区分检索失败、选文失败、证据理解、任务遗漏、格式与停止问题。

## 何时考虑 skill、训练或更多 Agent

- **静态 skill**：重复错误能明确写成步骤、检查表或工具使用规范时再实现加载器。固定提示与按需加载使用同样内容，记录选择和上下文成本。
- **微调**：错误稳定集中在某个模型能力，且具备可靠训练与独立评估标签时再推进。已有 SciFact LoRA 是摘要核验模块实验，采用门槛未通过；不转述为 Agent 效果提升。
- **经验更新**：先建立可信反馈、版本记录、选择集与独立确认集；未校准的模型自评不能直接批准经验更新。
- **多 Agent**：任务有明确独立子问题且协作收益可测时再比较，同时计算通信、重复搜索和额外模型成本。
